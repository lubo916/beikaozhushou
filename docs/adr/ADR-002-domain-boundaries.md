# ADR-002 领域划分

- 状态：已采纳

## 背景

附录 L 按页面的数据读写推出 15 个候选领域。通知与触达（S25 的提醒、S35、P15）、客服工单（P16、S35）、参数中心与端外壳（P19、分期规划 0.1c 与 0.1e）在这 15 个领域中没有合适的归属。功能 ID 前缀还要避开归档旧模块文档的模块编号，免得分拣时混淆。

## 决定

1. 采用 18 个领域（docs/product/domain-map.yaml）：附录 L 的 15 个，加 engagement（触达与增长）、support（客服与反馈）、platform（平台基础）。考试画像领域的代码取 EXM，与旧模块文档的模块编号区分。
2. learner 是证据与掌握档的唯一写入方：其他领域经 learner 的接口提交证据，由 learner 发出 evidence.* 业务事件（E-OWN-02）。记忆状态也归 learner。
3. 领域依赖单向，跨领域调用只经目标领域包的公开接口。到期队列的接口由 plan 定义，错题、卡片等由 practice 实现。
4. 每张表、每个业务事件、每个参数、每个 AI 场景、每个指标恰好归属一个领域，写在各自的 owner 字段。
5. 后台不是领域，后台页面的功能分别归属到对应领域。

## 后果

- 功能 ID 前缀共 18 个；跨领域契约的改动走重型通道。
- learner 的接口是热点，0 期先定（LRN-01）。
- 何时重新考虑：某个领域长期只有一两个功能，或两个领域的功能总是成对改动时，合并或拆分领域（重型通道）。
