# 默认验收与交付协议

策略版本：`2026-10-24.1`。本协议与 `AGENTS.md`、用户已有决定和任务简报共同使用；不扩大任务改动范围，不撤销业务确认、人工闸门、第三轮熔断或 B08 等既有前置。用户已授权的业务代选和页面效果复核继续按原授权范围执行，不新增“每批必须再等用户”的门槛。

## 默认流程

1. 从 Windows 接续新旧聊天，先运行 `pwsh -File .\bk-v4.ps1 status`，核对 Ubuntu V4 实际路径、分支、提交、策略版本；再读实际仓库的 `AGENTS.md` 和本协议。后续 bk 操作仍用同一入口。旧任务分支通过入口接入当前权威工具，不直接相信旧包自带工具已包含本策略；已运行的进程不会热替换。网页端 Claude 按新包 `START_HERE` 或接续说明，先读包外 `BK_RUNTIME/AGENTS.md`、`BK_RUNTIME/acceptance-flow.md` 与 `BK_RUNTIME/runtime.json`；所有 bk 命令均从 `repo/` 运行 `python3 ../BK_RUNTIME/bk.py`。旧任务 Git 树中的工具与规则仅保留来源，不执行旧 `repo/tools/bk.py`，也不向任务分支提交运行时升级。结果包和检查点包继续携带同一套已核验包外运行时；本地正式验收仍通过 Windows 权威入口。
2. 开发前确认任务范围、规则/决定版本及共享能力。新端首次使用的权限、依赖、生成目标、接口与壳测试缺口，由已授权的整合任务先补；页面任务不越界。
3. 交接前运行与本次改动相称的本页测试及廉价守卫。任一同源问题出现，协调者对在途任务做一次针对性扫描并分派修复，不逐页反复发现、反复讨论。不要额外复制一套全量预检；只有确能提前挡住已知风险、且不争用他人资源的检查才前移。
4. 使用现有交接单登记关键业务、跨页联动、实际完成范围与证据链接；未接通、未运行、待处理如实写明。不要求每句话单独证明，不把某任务的 55 项终审、多张卡片或专项数量推广成通用要求。
5. 正式验收由统一队列安排，重检查串行并持验证锁；正式整合还须确认主工作树所有权。排队期间可做不占共享端口、数据库或重检查资源的只读核对与本页准备。等待后只复核变化：候选/主干、任务范围、规则/授权、测试/配置/生成物、环境与证据身份；变化可能触及时，重验受影响部分，不按等待时长机械重做整页。
6. 正式 full 仍保留配置中的七项及用户既有 gate。默认按廉价到昂贵的阶段顺序运行，任一阶段失败立即停止后续阶段；未运行项写 `not_run`，不记为通过。通过阶段的日志保留，但本轮整体不放行。需要一次收集更多失败时才显式使用 `verify --diagnostic`；诊断报告永远不能用于合并或交付。
7. 每轮建立独立 `run_id`、输入身份、日志与摘要；完成时复核身份，合并前再次核对候选。中断、报告损坏、环境故障、身份变化或结果不完整都保留 pending，绝不借用其他任务、其他轮次或旧 `last-verify` 的绿色。
8. 正式截图覆盖目标视图时直接用于视觉复核；缺失视图才补拍。关键跨页点击按实际风险检查，能安全前移的前移。功能/规则缺陷保留可复现回归；纯排版、格式等低影响机械修正用对应文件核对、既有守卫和必要的受影响视图复核，不为机械改动新增镜像测试；正式七项 gate 保持。
9. 候选一致且 gate 全部满足后，才按既有流程合并、生成版本包。生成后及交付前核验非空、ZIP CRC、SHA256、任务/版本/基线、V4 身份和必要文件；使用正式来源的交付副本，恢复副本后重新核验。推送后只读核对远端 main、标签与目标提交。
10. 远端 CI 保留现行 `.github/workflows/verify.yml`：所有分支 push 和 pull request 触发，两个 `verify-shard` 分片共同完成 full，最终 `verify` 要求分片全部成功；观察对应运行的最终 `verify`，不按同 SHA 合并或跳过不同运行、矩阵、事件。保护规则和 rulesets 的只读 API 本次均返回 403，不能声称已核验为配置或未配置；其他用户既有远端要求继续适用。CI 失败先查产品、测试、环境、权限或配置原因，再决定修复、重跑或 revert，不一律回滚。

## 失败与恢复

| 情况 | 默认处理 |
| --- | --- |
| 产品或规则缺陷 | 保全日志，按现有范围/授权修复，补可复现回归，再重新正式验收。 |
| 测试实现错误或预期过期 | 写明错误原因；沿用 `--allow-test-change` 等既有审查，不放松正确断言。改后重新正式验收。 |
| 环境明确阻断 | 前检失败即停止；只处理自己的资源，不杀别的任务进程、不重置他人数据库或依赖。修复后重新验收。 |
| 中断、工具异常、报告或制品不完整 | pending，保存现场，核对进程、锁、候选与本轮产物；不得把工具 exit 1 等同产品测试失败，也不得把旧摘要当本轮成功。 |
| flaky、超时、exit 139 或未知失败 | 保留原始失败/重试次数，先归因。未改该页面、几次定向重跑绿均不足以证明环境原因或自动放行；需要具体风险判断，未解决的阻断保持 pending。 |
| 门槛未满足、第三轮熔断、授权不足或用户要求先看 | 沿用既有暂停/升级规则；已有授权范围不重复索取许可。 |

队列/锁只约束本次协议接入的协作流程；主工作树还必须由协调者按 grant/授权分配。不得绕过入口启动另一个旧控制器来抢占目录。遗留进程须先确认身份和状态，不能为“清环境”删除日志或强杀他人工作。

## 证据身份与暂不开启的优化

报告以候选与实际输入为准，至少关联策略版本、运行编号、源/候选提交与 tree、被测输入、检查配置/命令、运行环境和日志哈希。哈希用于发现输入变化，不能证明业务正确；提交相同也不自动表示依赖、夹具、浏览器、环境、配置或外部状态相同。

阶段续跑、只改测试/文档时复用浏览器结果、多个任务合批放行、影响分析选测、正式重检查并发：**默认关闭，仍按完整单候选 full 验收**。它们需要后续独立影子试验、覆盖证明与明确启用决定，不因本协议自动获得授权。整批候选通过不能证明逐个发布的中间状态已经通过。

## 部署与生效核对

以下是工具自动输出/维护者部署核对，不是给每个任务新增手工材料。

- 入口身份：部署后，`bk-v4.ps1 status` 必须对应真实 Ubuntu V4；`bk-v4.ps1 acceptance policy` 显示工具 `4.2.0`、策略 `2026-10-24.1`、`default_fail_fast: true`、`diagnostic_can_release: false`、`unknown_flaky_blocks: true`，自动续跑/合批/缩套件为 false。入口从权威 main 取当前工具及辅助模块，旧分支不降级；策略不匹配或缓存校验失败不得继续。旧聊天先执行入口再读当前规则，已运行进程不自动切换。
- 网页端新包：包根 `BK_RUNTIME/` 含 `bk.py`、`bk_acceptance.py`、`AGENTS.md`、`acceptance-flow.md` 和 `runtime.json`；清单记录工具/策略版本、权威来源提交及四个载荷文件的大小/SHA256，工具核验后接续。装载包外运行时本身不改变任务 Git HEAD/来源树；旧包不能自行获得新默认，需通过新包的 `START_HERE` 接续。缺失或摘要不符时保留现场、停止沿用，不回退执行旧树工具。
- 调用方式：正常 `verify --level quick|web|full` 默认 failfast；`verify --level full --diagnostic` 只用于诊断。`done/in` 继续走既有整合入口与 grant，不把单独 verify 或诊断结果当合并凭据。
- 运行摘要：当前工作树 `.bk/acceptance/runs/<run_id>/` 保存 `run.json`、`summary.json`、阶段日志及浏览器证据；`.bk/last-verify.json` 仅为本轮原子兼容镜像。摘要有 `run_id`、`policy_version`、`task`、`identity`、`mode`、`status`、`level`、`verdict`、UTC 起止与 `duration_seconds`；已运行阶段有耗时、日志/哈希与分类，未运行阶段明确 `not_run`。身份含被测内容、配置、命令、实际运行环境及运行输入哈希。缺必要证据、旧策略或身份不一致时不得借用通过结果。
- failfast：用隔离的工具测试确认前段失败后后项为 `not_run`、整体非 pass；不在真实产品上故意引入错误验证部署。
- 诊断与中断：隔离测试确认 diagnostic 即使项目检查通过仍不可放行；中断产生不完整/pending 状态，本轮不能回退借用上一轮摘要。`--continue` 遇候选或日志变化须撤销 verified 并重新完整验收和原 gate；`release_pending` 续收仅同版本重出包，不增版；已合主干后不允许 `--abort`。
- 队列/锁：common 主树 `.bk/acceptance/queue/*.json` 保存单请求记录，重检查共用 `.bk/parallel/verify.lock`；`acceptance status` 显示 waiting/running，进程真实性以 PID 与 start_ticks 核验，遗留条目不能当活进程。摘要 `queue` 关联 `request_id`、`operation`、`wait_seconds`。隔离工具测试确认两个接入入口互斥、父进程退出后仍在运行的子进程继续持锁；整合另核主树所有权，结束后保留证据。
- 制品/远端：发布入口完成非空/解析/版本来源校验及远端提交、标签核对。推送后观察现行 workflow 的最终 `verify`，两个分片不能少等；保护/rulesets API 403 记录为未知，不能推断存在或不存在保护。不能仅凭本地 exit 0 宣称所有远端 gate 已满足。
- 计时与分类：`bk-v4.ps1 acceptance metrics` 汇总本工作树各轮的起止、等待、耗时、阶段结果和诊断标识，不另造表；`acceptance triage --log <日志> --exit-code <码>` 只分类，不修复、不重试、不放行。自动指标仍不是任务端到端时间；交接到远端完成、预检开销、合并后发现的问题若未记录则明确缺失，不能从命令/回合/持锁时间相加推导。

上述接口已在本次独立实现树对齐；上线状态以权威 main 提交、Windows 入口部署、工具针对性测试与实际输出为准，不能把独立树写完当成已部署。环境前检目前只读核对必需脚本、命令运行器及配置要求的浏览器/数据库可达性，不代表磁盘、全部系统库或所有依赖均已体检。合法、新鲜、完整的 Playwright JSON 才能作为证据；flaky、skipped、unexpected 和 errors 均阻断。已运行的旧进程按其原版本结束或安全停止，下一轮通过权威入口启用新策略。
