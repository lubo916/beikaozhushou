## 规格的硬要求（Codex 会逐条机检）
- **结构**：
  - 七节齐全：1 目标与边界、2 业务规则、3 界面、4 数据、5 AI 行为、6 验收、7 不变量与合规；正文不超过 6,000 字符。
  - front matter 只有 id、status、refs、open_questions；标题、领域、依赖与覆盖条目以 roadmap.yaml 为准，不在规格里重复。
- **规则与验收**：
  - 规则编号只用 R1 至 R9：两位数的规则编号会被深化来源编号检查（E-REFINE-03）当成外部编号拦下。一条规则可以有几句，但每句都能判定对错。
  - 验收用 Given/When/Then，编号 <ID>-AC<n>；每条规则至少被一条验收覆盖；切片验收句与覆盖条目都要落到规则或验收。
- **登记与引用**：
  - 默认值写参数名，不写数字；新参数在 contracts/params.yaml 登记，字段齐全，没有原型条目的在说明末尾注明依据。
  - 正文提到的接口、表、事件、错误码、参数、数据类别、指标、INV、ADR 都列进 refs（E-REF-02）。
- **措辞**：只写现状，不出现“原来、改为、之前、原方案、已调整、调整为、此前”；术语以 glossary 为准，不用禁用同义词与宣传禁用语。
- **体量**：第 3 节只写相对页面登记与 ui-states 约定的例外。这一节点名的页面会把整页登记带进任务包，只点名真正需要的页。packs/<ID>.md 口径的任务包不超过 15,000 字符。
- **未决与范围**：
  - 需要业务决定、依据里又找不到答案的，写进 open_questions（OQ-<ID>-<n>），每条给临时默认。
  - 不把未决事项写成定论，不扩大范围；只写规格要求的行为，实现层面的做法（库、类型、文件结构）留给计划。
