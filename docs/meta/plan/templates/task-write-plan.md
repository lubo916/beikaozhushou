## PLAN.md 的格式（handoff.py 逐项解析，写错会被拒收）
第一节固定如下，项名与顺序不改：

## 计划（确认后才动代码）
- 改动文件：
  - <仓库相对路径>（中文说明）
- 参考文件：
  - <仓库相对路径>（中文说明）
- 契约变更：……（没有写“无”）
- AC → 测试：
  - <ID>-AC<n> → <测试文件>：[<ID>-AC<n>] <测试标题>
- 实现要点：……
- 风险与不确定：……
- 确认：（谁、何时）

写法：
- **改动文件**：实现时能改的全部范围（测试文件不必列）。
  - 每行一个路径，说明只用中文写在其后的括号里；以 / 结尾表示该目录下都可改。
  - 仓库根下名字带两个点的文件写成 ./ 开头（如 ./vitest.config.ts），否则解析不出。
  - 不列 scripts/、docs/meta/、design/screens/、work/、AGENTS.md 与带 GENERATED 标记的文件。
- **参考文件**：只列仓库里已有、实现时要看原文的文件。包里没有又必须看的，写进“需要补充的文件”。
- **AC → 测试**：
  - 每条 AC 至少对应一个测试，测试标题带 [<ID>-AC<n>]；以测试执行的不变量另写 [INV-<nn>]。
  - 测试位置按约定：单元测试与源文件同目录，端到端测试在 tests/e2e/，金标数据在 tests/fixtures/。
- **契约变更**：只能是规格已写明的。规格没写、实现又需要的，写进“对规格的疑问”，不要自己加。
- **实现要点**：写给实现时的自己，包括结构、关键做法、边界情形，以及怎样避免裸阈值、不越过依赖方向。
- **确认**：这一行保持“（谁、何时）”，产品负责人确认后由 Codex 填写。

第一节之后可以再有两节：
## 需要补充的文件（每行一个仓库路径，下一轮补进包里）
## 对规格的疑问（规格缺信息、冲突或含糊之处；Codex 会转给负责人，或退回规格修改）
